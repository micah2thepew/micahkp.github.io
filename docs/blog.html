From Monthly Payments to Meaningful Features: A pandas Tutorial

Introduction

Each client in this dataset has six months of payment history, but the monthly columns can make it hard to spot patterns at a glance. In this tutorial, we’ll use pandas to turn that history into a few interpretable features, such as the number of late-payment months and whether late payments became more common recently. Feature engineering means creating useful new variables from data that’s already available. These summaries make patterns easier to explore and can serve as inputs for a model later.

Overview of the Feature Engineering Process

Each row represents one client. We’ll turn six months of payment information into a few features that are easier to compare:

  • Put the months in order. The payment-status columns run from PAY_6 (earliest) to PAY_0 (most recent). The UCI dataset description explains what each column records.
  • Count late months. Mark payment-status values greater than zero as delays, then count the delayed months for each client.
  • Compare earlier and recent behavior. Split the six months into two groups of three and compare their late-payment rates.
  • Summarize bill amounts. Calculate the average bill in each three-month period and find the difference.
  • Keep the outcome separate. Do not use default payment next month to calculate features from the previous six months.

Step 1: Load the data and identify the months

Download the Excel file from the UCI link above and save it in a data folder beside this tutorial. The first spreadsheet row uses generic labels such as X1, while the second has descriptive names such as LIMIT_BAL and PAY_0. Setting header=1 tells pandas to use that second row as the column names. We also strip any surrounding spaces from those names and print a preview to check that the file loaded as expected. If pandas asks for an Excel reader, install the xlrd package for this older .xls file.

The data is arranged in wide form: each client has one row, and separate columns hold the monthly values. That means we can calculate a summary across columns within each row. The payment-status names are unusual: there is no PAY_1, and PAY_0 is the most recent month. Listing the actual column names in time order prevents us from accidentally comparing the wrong months.

Step 2: Create late-payment features

We define the earlier period as the first three months and the recent period as the last three. In the code below, .gt(0) asks whether each payment-status value is greater than zero. It returns True for a delayed month and False otherwise. Since pandas treats True as 1 when calculating a sum, .sum(axis=1) counts late months across each client’s row. Taking the mean of those same Boolean values gives the fraction of months with a delay.

payment_cols = ["PAY_6", "PAY_5", "PAY_4", "PAY_3", "PAY_2", "PAY_0"]
earlier_cols = ["PAY_6", "PAY_5", "PAY_4"]
recent_cols = ["PAY_3", "PAY_2", "PAY_0"]

late = df[payment_cols].gt(0)
df["late_months_6m"] = late.sum(axis=1)

df["late_rate_earlier3"] = df[earlier_cols].gt(0).mean(axis=1)
df["late_rate_recent3"] = df[recent_cols].gt(0).mean(axis=1)
df["late_rate_change"] = (
    df["late_rate_recent3"] - df["late_rate_earlier3"]
)

The axis=1 argument is important: it tells pandas to work across columns for each client, rather than down a column across different clients. late_months_6m ranges from 0 to 6. Each three-month late rate ranges from 0 to 1. Subtracting the earlier rate from the recent rate creates late_rate_change: a positive value means delays were more frequent recently, a negative value means they were more frequent earlier, and zero means the rates were the same. This describes a pattern; it does not tell us why the pattern occurred.

Step 3: Check one client’s history

A worked example helps us see where the new numbers come from. The next block selects client 1 by ID, then prints the six original payment-status values beside the features we created. ID identifies the row for inspection; it is not one of our payment-behavior features. The .round(2) call makes the rates easier to read without changing the underlying values.

raw_columns = ["ID"] + payment_cols
feature_columns = [
    "ID",
    "late_months_6m",
    "late_rate_earlier3",
    "late_rate_recent3",
    "late_rate_change",
]

client_one = df.loc[df["ID"] == 1]

print("Original payment-status values:")
print(client_one[raw_columns].to_string(index=False))

print("\nFeatures created from those values:")
print(client_one[feature_columns].round(2).to_string(index=False))

The table condenses the six original payment-status columns into values we can explain in one sentence: client 1’s late payments were concentrated in the recent period. We can repeat this calculation for every client because pandas applies each row operation to the whole DataFrame.

Step 4: Summarize bill amounts

The dataset also records each client’s monthly bill amounts. BILL_AMT6 is the earliest of the six bill columns, and BILL_AMT1 is the most recent. We calculate the average bill for the earlier three months and for the recent three months. Their difference, bill_change, describes how the typical bill amount changed between those periods. This is an amount difference, rather than a percentage, so it still works when an earlier bill is zero.

earlier_bills = ["BILL_AMT6", "BILL_AMT5", "BILL_AMT4"]
recent_bills = ["BILL_AMT3", "BILL_AMT2", "BILL_AMT1"]

df["avg_bill_earlier3"] = df[earlier_bills].mean(axis=1)
df["avg_bill_recent3"] = df[recent_bills].mean(axis=1)

df["bill_change"] = df["avg_bill_recent3"] - df["avg_bill_earlier3"]

A positive bill_change means the recent average was higher; a negative value means it was lower. A larger bill alone does not establish that a client is more likely to default. To inspect the finished features, select a few relevant columns and display the first five clients:

Conclusion: Put the features to work

We have turned six monthly payment-status values into a late-month count and a measure of how delays changed over time. We also compared average bill amounts across the same two periods. Each feature has a specific meaning, which makes the resulting table easier to inspect than the original monthly columns alone. None of these calculations uses default payment next month, so the summaries describe information available before that outcome.

Try this next: when you are ready to build a default-prediction model, compare two versions using the same train/test split. Give one model the original monthly payment-status and bill-amount columns; give the other those same columns plus late_months_6m, late_rate_change, and bill_change. Evaluate both on the same held-out clients with the same metric. The engineered features make frequency and recent changes explicit for the model. If the second version performs better, you have evidence that those summaries helped; if it does not, try a different summary and compare again.
